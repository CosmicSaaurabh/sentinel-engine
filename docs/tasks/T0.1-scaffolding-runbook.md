# T0.1 Runbook: Project Scaffolding

Companion to issue #1 and the T0.1 entry in `docs/tasks/mvp-task-breakdown.md`.
This is a hands-on runbook, not generated code.
Type every file yourself.

Build tool: Maven, not Gradle.
The task breakdown originally specified Gradle; it and CLAUDE.md have both been amended to Maven, since you already know Maven well and fighting an unfamiliar build DSL is not the learning goal of this project (CLAUDE.md rule 5's explicit tooling exception).
The module boundaries and every Java/SQL/YAML file below are unchanged; only the build wiring differs.

## 0. Versions this runbook assumes

- Java on `PATH`: whatever you have (checked: JDK 25 locally). Maven's `maven.compiler.release=21` targets bytecode/API level 21 regardless of which JDK actually runs the build, so no toolchain plugin is needed. See the callout in step 2 if you want a bit-for-bit JDK 21 runtime later.
- Maven: `3.9.11` found locally; the wrapper pins `3.9.16` so the repo is reproducible on any machine without relying on what's globally installed.
- Spring Boot: `4.1.0`.
- PostgreSQL: `18.4`.
- Key plugin/BOM versions (checked against Maven Central on 2026-07-29): `maven-compiler-plugin 3.15.0`, `maven-surefire-plugin 3.5.6`, `maven-wrapper-plugin 3.3.4`, `spring-boot-maven-plugin 4.1.0`.

One structural note before you start: this is a **multi-module** Maven build where only `engine` is a Spring Boot application.
`worker-sdk` and `proto` must never depend on Spring (T2.4's DoD).
The standard `spring-boot-starter-parent` inheritance model doesn't fit that, because a POM can only have one `<parent>`, and that parent would have to be shared by all three modules.
Instead the root aggregator POM imports the `spring-boot-dependencies` BOM via `<dependencyManagement>` (not by inheriting `spring-boot-starter-parent`), so all three modules share version management, but only `engine`'s POM actually lists a Spring dependency.
`worker-sdk` and `proto` structurally cannot pull in Spring by accident, the same guarantee the Gradle version of this runbook got from giving them only the `java-library` plugin.

### Local Docker environment: Colima, not Docker Desktop

If `docker context show` reports `colima` (check with `colima status`), two things need to be set up once per machine before the Testcontainers smoke test in step 8 will pass:

1. **Point Testcontainers at the Colima socket.** It doesn't reliably auto-detect non-default Docker contexts. Create `~/.testcontainers.properties` (a personal machine file, not part of the repo) containing:
   ```
   docker.host=unix:///Users/<you>/.colima/default/docker.sock
   ```
2. **Disable Ryuk.** Ryuk (Testcontainers' resource-reaper sidecar) bind-mounts the Docker socket into itself for cleanup duty. Colima's virtiofs mount can't bind-mount a Unix socket special file that way, and container startup fails with `error while creating mount source path '...docker.sock': mkdir ... operation not supported`. This is a documented Colima limitation, not a project bug. Work around it by exporting, in your shell profile (`~/.zshrc`):
   ```
   export TESTCONTAINERS_RYUK_DISABLED=true
   ```
   Trade-off: Ryuk is what guarantees stray containers get cleaned up if the JVM is killed ungracefully mid-test. With it disabled, an occasional `docker ps -a` / `docker container prune` is worth doing to catch orphaned Postgres containers. CI runs on `ubuntu-latest` with standard Docker, so Ryuk works normally there — this only affects local Colima setups, never CI.

## 1. Root aggregator POM and the Maven wrapper

Maven is already on your `PATH` (`3.9.11`), so bootstrap the wrapper directly rather than harvesting a zip:

```bash
cd /Users/saurabhmishra/Desktop/projects/sentinel-engine
mvn -N wrapper:wrapper -Dmaven=3.9.16
chmod +x mvnw
./mvnw --version
```

This drops `mvnw`, `mvnw.cmd`, and `.mvn/wrapper/maven-wrapper.properties` into the repo, pinned to Maven `3.9.16`.
Anyone who clones the repo — including CI — now runs the exact same Maven version without installing it globally.

(If a machine has no `mvn` on `PATH` at all: `https://start.spring.io` with `type=maven-project` also ships a working `mvnw`/`mvnw.cmd` pair you can copy in, the same trick used for the Gradle wrapper earlier.)

Now the root `pom.xml`:

```xml
<?xml version="1.0" encoding="UTF-8"?>
<project xmlns="http://maven.apache.org/POM/4.0.0"
         xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance"
         xsi:schemaLocation="http://maven.apache.org/POM/4.0.0 http://maven.apache.org/xsd/maven-4.0.0.xsd">
    <modelVersion>4.0.0</modelVersion>

    <groupId>dev.sentinel</groupId>
    <artifactId>sentinel-engine</artifactId>
    <version>0.0.1-SNAPSHOT</version>
    <packaging>pom</packaging>

    <modules>
        <module>engine</module>
        <module>worker-sdk</module>
        <module>proto</module>
    </modules>

    <properties>
        <project.build.sourceEncoding>UTF-8</project.build.sourceEncoding>
        <maven.compiler.release>21</maven.compiler.release>
        <spring-boot.version>4.1.0</spring-boot.version>
    </properties>

    <dependencyManagement>
        <dependencies>
            <dependency>
                <groupId>org.springframework.boot</groupId>
                <artifactId>spring-boot-dependencies</artifactId>
                <version>${spring-boot.version}</version>
                <type>pom</type>
                <scope>import</scope>
            </dependency>
        </dependencies>
    </dependencyManagement>

    <build>
        <pluginManagement>
            <plugins>
                <plugin>
                    <groupId>org.apache.maven.plugins</groupId>
                    <artifactId>maven-compiler-plugin</artifactId>
                    <version>3.15.0</version>
                    <configuration>
                        <release>21</release>
                        <compilerArgs>
                            <arg>-Xlint:all</arg>
                            <arg>-Werror</arg>
                        </compilerArgs>
                    </configuration>
                </plugin>
                <plugin>
                    <groupId>org.apache.maven.plugins</groupId>
                    <artifactId>maven-surefire-plugin</artifactId>
                    <version>3.5.6</version>
                </plugin>
                <plugin>
                    <groupId>org.springframework.boot</groupId>
                    <artifactId>spring-boot-maven-plugin</artifactId>
                    <version>${spring-boot.version}</version>
                </plugin>
            </plugins>
        </pluginManagement>
    </build>
</project>
```

Notes:

- No `junit-bom` or `testcontainers-bom` import here on purpose. `spring-boot-dependencies` already manages compatible JUnit Jupiter and Testcontainers versions for the starters used below. Importing the latest upstream JUnit/Testcontainers BOMs yourself (JUnit is at a `6.x` major, Testcontainers at a `2.x` major as of this check) would fight Boot's own managed versions and risk an incompatible combination — let Boot own it.
- `-Xlint:all -Werror` on the compiler plugin is the direct Maven equivalent of the Gradle root config: warnings fail the build, from day one, same rationale as before — a raw-type or unchecked-cast warning is cheap to fix today and expensive to discover later.
- `maven.compiler.release=21` compiles against the Java 21 language/API level using whatever JDK actually runs Maven (25 locally). This is not the same guarantee as Gradle's toolchain auto-provisioning, which downloads and *runs on* a real JDK 21. If you later want byte-for-byte JDK 21 execution (not just API-level 21 compilation), that requires either installing Temurin 21 locally (`brew install --cask temurin@21`) and registering it in `~/.m2/toolchains.xml` with `maven-toolchains-plugin`, or running CI on an actual JDK 21 runner. Not needed for T0.1; flag it if a later phase's behavior seems to depend on runtime JDK version specifically.

## 6. Application configuration

`engine/src/main/resources/application.yaml`:

```yaml
spring:
  application:
    name: sentinel-engine
  datasource:
    url: jdbc:postgresql://localhost:55432/sentinel
    username: sentinel
    password: sentinel
    hikari:
      maximum-pool-size: 5
      minimum-idle: 5
      connection-timeout: 2000
      validation-timeout: 1000
      max-lifetime: 1800000
      leak-detection-threshold: 30000
  flyway:
    enabled: true
    locations: classpath:db/migration
    baseline-on-migrate: false

management:
  endpoints:
    web:
      exposure:
        include: health,prometheus
  endpoint:
    health:
      show-details: always
```

Same reasoning as before on every Hikari value: `maximum-pool-size: 5` is deliberately below Hikari's own default of 10 so T1.4's 50-parallel-claimer test hits real contention; `connection-timeout: 2000` makes exhaustion fail fast instead of queueing forever; `leak-detection-threshold` is off by default in Hikari and is turned on here.

## 8. Application class and Testcontainers smoke test

`engine/src/main/java/dev/sentinel/engine/EngineApplication.java`:

```java
package dev.sentinel.engine;

import org.springframework.boot.SpringApplication;
import org.springframework.boot.autoconfigure.SpringBootApplication;

@SpringBootApplication
public class EngineApplication {

    public static void main(String[] args) {
        SpringApplication.run(EngineApplication.class, args);
    }
}
```

`engine/src/test/java/dev/sentinel/engine/TestcontainersConfiguration.java`:

```java
package dev.sentinel.engine;

import org.springframework.boot.test.context.TestConfiguration;
import org.springframework.boot.testcontainers.service.connection.ServiceConnection;
import org.springframework.context.annotation.Bean;
import org.testcontainers.postgresql.PostgreSQLContainer;
import org.testcontainers.utility.DockerImageName;

@TestConfiguration(proxyBeanMethods = false)
class TestcontainersConfiguration {

    @Bean
    @ServiceConnection
    PostgreSQLContainer postgresContainer() {
        return new PostgreSQLContainer(DockerImageName.parse("postgres:18.4"));
    }
}
```

`PostgreSQLContainer` is not generic in Testcontainers 2.x (the line Boot 4.1.0 manages) — it directly extends `JdbcDatabaseContainer<PostgreSQLContainer>` internally rather than exposing a type parameter to callers, unlike the old 1.x self-bounded-generic pattern. Use the plain type, no `<?>` and no diamond.

`engine/src/test/java/dev/sentinel/engine/EngineApplicationTests.java`:

```java
package dev.sentinel.engine;

import static org.junit.jupiter.api.Assertions.assertEquals;

import javax.sql.DataSource;
import org.junit.jupiter.api.Test;
import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.boot.test.context.SpringBootTest;
import org.springframework.context.annotation.Import;
import org.springframework.jdbc.core.JdbcTemplate;

@Import(TestcontainersConfiguration.class)
@SpringBootTest
class EngineApplicationTests {

    @Autowired
    private DataSource dataSource;

    @Test
    void flywayBaselineAppliedAgainstRealPostgres() {
        JdbcTemplate jdbcTemplate = new JdbcTemplate(dataSource);

        Integer appliedMigrations = jdbcTemplate.queryForObject(
                "select count(*) from flyway_schema_history where success = true",
                Integer.class);

        assertEquals(1, appliedMigrations);
    }
}
```

This proves Flyway actually ran against real Postgres, not just that the Spring context started.

## 9. GitHub Actions CI

`.github/workflows/ci.yml`:

```yaml
name: CI

on:
  push:
    branches: [main]
  pull_request:

jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - name: Set up JDK 21
        uses: actions/setup-java@v4
        with:
          distribution: temurin
          java-version: '21'
          cache: maven

      - name: Build
        run: ./mvnw --batch-mode verify
```

`ubuntu-latest` ships Docker pre-installed, so the Testcontainers-based test runs in CI with no extra service container config.
`cache: maven` on `actions/setup-java` caches `~/.m2/repository` between runs — the direct Maven equivalent of the `gradle/actions/setup-gradle` caching used in the earlier Gradle version.
`--batch-mode` suppresses interactive/ANSI output noise in CI logs.

## 11. Verify the full DoD

```bash
# 1. Clean build, all three modules resolve.
./mvnw clean verify

# 2. Postgres is up and the engine connects and migrates.
docker compose -f infra/docker-compose.yml up -d
./mvnw -pl engine spring-boot:run &
sleep 5

# 3. Exactly one applied migration.
docker exec -it sentinel-postgres psql -U sentinel -d sentinel \
  -c "select version, description, success from flyway_schema_history;"

# 4. Testcontainers integration test passes (already ran as part of `verify`,
#    rerun in isolation if you want to see it alone).
./mvnw -pl engine test

# 5. Actuator endpoints respond.
curl -s localhost:8080/actuator/health
curl -s localhost:8080/actuator/prometheus | head -5

kill %1   # stop the background spring-boot:run
```

Then push a branch and confirm CI goes green from a clean clone.
